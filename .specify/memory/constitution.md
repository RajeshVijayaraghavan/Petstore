# Petstore Web Console Constitution

## Core Principles

### I. Contract Compliance

The Petstore REST API (OpenAPI 3.0.4, v1.0.27) is a fixed external service that
this console consumes as-is. The console MUST NOT invent endpoints, extend
payloads, or work around API limitations with a backend-for-frontend layer. All
client-side types, query hooks, and mock servers MUST be auto-generated from the
OpenAPI spec via Orval. Hand-written API types are forbidden. When the upstream
spec changes, regenerate and let the compiler surface every affected call site.

### II. Design-System Fidelity

The Stitch design system ("The Curated Console") is the authoritative visual
specification. Every screen MUST follow its Material 3 tonal palette tokens,
Manrope/Inter typography pairing, No-Line Rule (boundaries via surface-color
shifts, never 1px borders), vertical indicator-pill navigation, and glassmorphism
for modals. Deviations require written justification in a PR description and
approval from the team.

### III. Type Safety End-to-End

TypeScript strict mode (`"strict": true`) MUST be enabled with no escape hatches
(`any`, `@ts-ignore`, `as unknown as T` casts). Zod schemas generated by Orval
validate API responses at runtime boundaries. React Hook Form resolvers use these
same Zod schemas so form validation and API validation are always in sync. The
goal is zero runtime type errors in production.

### IV. User-Friendly Errors Always

No raw HTTP status codes, stack traces, or technical jargon may reach the user
interface. Every API error MUST be mapped through a centralized error-mapper
(`lib/error-mapper.ts`) to a plain-language message with a suggested corrective
action. Network failures MUST show a global connection-error banner with a
"Retry" option. Loading states MUST appear within 200ms of any data request.
Write operations MUST disable the submit control while in flight to prevent
double-submission.

### V. Simplicity & YAGNI

Start with the simplest implementation that satisfies the spec. No feature,
abstraction, or library may be added unless it is required by a current user
story. Specifically:

- No backend code, SSR, server components, or BFF layer. This is a browser SPA;
  if a feature cannot be implemented without a backend change, it is out of scope
  until the upstream API is extended.
- No state management beyond TanStack Query (server state) and a single Zustand
  store (client state). No Redux, no Context-heavy patterns.
- No component library beyond shadcn/ui primitives. No Ant Design, no MUI.
- No charts, analytics dashboards, or time-series data until a future spec
  explicitly requires them.
- Client-side pagination and sorting are acceptable for v1 data volumes; do not
  introduce virtual scrolling or server-side pagination unless proven necessary.
- Extended pet attributes (pricing, breed, gender, weight, SKU, location) are
  out of scope for v1 regardless of wireframe aspirations.
- Mobile-phone optimization is out of scope for v1.

### VI. Accessible & Responsive

All interactive elements MUST be keyboard-navigable and use appropriate ARIA
attributes (provided by Radix UI primitives via shadcn/ui). Color contrast MUST
meet WCAG 2.1 AA for all text on surface combinations. The layout MUST work on
desktop (1280px+) and tablet (768px–1279px) without horizontal scrolling or
overlapping content.

### VII. Feature-Folder Organization

UI code MUST be organized by feature domain, not by technical role. Each feature
area (pets, orders, inventory, users) has its own folder under `components/`
containing all components specific to that feature. Shared primitives live in
`components/ui/` (shadcn) and `components/layout/` (shell, sidebar, navbar).
Pages in `pages/` compose feature components but contain no business logic
themselves. This structure ensures each feature can be developed, reviewed, and
tested in isolation without touching unrelated code.

```
frontend/src/
├── components/
│   ├── ui/               # shadcn/ui shared primitives
│   ├── layout/           # AppShell, Sidebar, Navbar
│   ├── pets/             # PetCard, PetForm, PetDetail, PetFilters
│   ├── orders/           # OrderForm, OrderDetail, OrderSearch
│   ├── inventory/        # InventorySummary, StatusCard
│   └── users/            # UserForm, UserProfile, UserSearch
├── pages/                # Route-level screens (compose feature components)
├── api/                  # Orval-generated (never hand-edited)
├── stores/               # Zustand (auth, UI preferences)
└── lib/                  # api-client, error-mapper
```

## Technology Stack

The canonical technology stack is maintained in

amendment.

## Governance

This constitution supersedes all ad-hoc decisions. Any code review or PR MUST
verify compliance with the principles above.

**Amendments**: Any change to this constitution requires:

1. A written proposal explaining the change and its rationale.
2. An update to this document with a version bump following semantic versioning:
   - **MAJOR**: Principle removal or backward-incompatible redefinition.
   - **MINOR**: New principle or section added, or material expansion.
   - **PATCH**: Clarification, wording fix, or non-semantic refinement.
3. A review of dependent artifacts (plan-template, spec-template, tasks-template,
   and downstream docs under `docs/`) to verify alignment, documented in a Sync
   Impact Report comment at the top of this file.

**Complexity justification**: If a feature implementation must violate a
principle (e.g., introducing a new state library, adding SSR), the plan.md
Complexity Tracking table MUST document the violation, why it is needed, and
which simpler alternative was rejected.
